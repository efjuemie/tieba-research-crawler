# 正式采集前稳定性验收摘要

更新：2026-11-16。旧版预检结果作为历史基线保留。统一发布列表和重复页保护已实现，自动化回归及 SDK 第 71–75 页列表写入验收通过。

**总体判断：2021—2026 年主题全量覆盖仍为 INCONCLUSIVE。** SDK 第 71–75 页列表验收通过，但没有验证 2021 年以来的全量列表、详情或网页补采。目前不建议以该时段完整覆盖已验证为前提启动正式采集。

## 旧版分页策略的预检基线

- **普通主题流**：第 1–70 页连续通过，最后成功页最早主题日期为 2026-05-05。第 71 页请求和响应页号一致，响应含 28 条唯一主题记录。按 API 返回／解析的置顶标记处理后，页内创建时间仍有约 20 分钟逆序；raw 与 DTO 时间顺序一致，没有解析回退或转换差异。程序将该页记为失败／不完整，没有跳过或标为完成。受控重放的页面指纹与首次失败相同，确认该次逆序不是一次性变化；该旧策略复测中的真实请求已停止。该流尚未到达 2021 年。
- **精华主题流**：第 1 页最早到达 2016 年；第 2 页重放仍出现跨页创建时间回跳，虽然该页内部排序正常，程序仍将其记为失败／不完整。该流能否完整到达 2021 年尚未证明。

这些页数是主题列表发现与持久化检查结果；本轮没有为相应页面运行完整的详情或网页补采工作器。这不表示已采齐这些主题的首楼、回复、楼中楼或正文，也没有导出新的正式研究语料。

普通流第 71 页的原始响应和 DTO 中，28 条记录的 `is_top` 解析值均为 false。该字段是没有 presence 证明的 protobuf 标量，因此这里只报告接口返回／解析值，不将其当成逐条网页核验过的置顶结论。

以上是旧版按创建时间顺序检查普通与精华双流时的结果。该实现把异常页面保留为失败／不完整，没有跳过后标为正常结束；这些记录不表示新策略已经运行或验证。

## 新回溯列表策略（已实现，自动化回归通过）

- 回溯目标为统一使用“发布”排序列表，不再单独扫描精华列表；每个主题继续保存 API 提供的 `is_good` 字段。按 TID 去重；创建时间乱序本身不再暂停回溯。
- 重复页保护按同一 run、同一列表流计算：一页中去重后的唯一非置顶 TID，至少 90% 已在该流先前页出现时，该页计为一次重复命中。连续 3 页命中才暂停该流。恢复时重读的页和置顶 TID 均不参与计算；此规则只用于 `backfill`，不用于 `periodic` 的 REPLY 首页监控。
- 贴吧 PC 页“最新”使用 `sort=0`，“发布”使用 `sort=1` 和 `frs/page_pc`；现有 SDK 的 CREATE 请求也使用 `sort=1`，但走不同的 `frs/page` endpoint 和客户端。有限样本中，发布页的 10 个 TID 也出现在 SDK 发布列表；一个普通列表样本含 19 条按 API 标记为非置顶且 `is_good=true` 的主题。这只支持排序请求语义，不证明两个 endpoint 的所有响应等价。SDK 按页请求并收到第 71–75 页，当前 worker 与 DataStore 的隔离列表写入验收通过；第 71 页创建时间逆序记为警告，数据保存后继续处理了后续页面。既有精华检查点摘要一致，核心主题记录仍保留且身份未变，既有列表记录没有重复 TID。该次验收没有运行详情或网页工作器，也不证明所有深页等价。
- 旧精华数据与 checkpoint 保留为历史审计材料；不会仅因切换策略就把旧 failed/incomplete 状态改成 completed。

## 已通过的稳定性检查

- 基线 HEAD `4db3217` 的全仓测试为 **640 passed、10 skipped**；旧版预检全仓回归为 **654 passed、10 skipped、18 warnings**。这些是历史结果，不代表新策略。
- 新策略实现后的全仓回归为 **672 passed、10 skipped、18 warnings**。两组隔离 PostgreSQL 回归各通过 2 项，共 **4 passed**；两库均无遗留行。Ruff、compile 和 diff 检查通过，独立最终代码复审未发现阻断问题。
- 此前定向合成回归为 **22 passed、4 skipped**。它与当前 SDK 列表写入验收范围不同，均不证明全量历史覆盖。
- R1–R3 隔离 PostgreSQL／模拟 API 演练通过。SIGINT 发出后，已接收的第 3 页完成提交；同一 run 恢复时重放最近完成的非终止第 3 页，再推进到第 4 页。旧版两条 CREATE 流的独立检查点和规范 ID 去重通过；checkpoint 提交前注入故障后重试通过。
- 此前 a0 旧版预检阶段，为避免恢复时选中不同运行模式的 run，恢复查询增加了模式筛选；跨模式误选在隔离 PostgreSQL 中复现并确认被拒绝。当时生产源码只改了这一项条件，独立最终复审覆盖 4 个代码文件且未发现阻断问题。此记录描述旧版预检，不代表当前统一列表策略的改动范围。
- 一个历史 PID 错配样本的当前网页候选通过只读身份检查：主题、楼层、评论、父楼、作者和论坛等 8 项标识一致；规范数据未写入，内容哈希未变。此结果只覆盖一个 `web_network` 候选路径，不能代表所有旧样本或所有网页来源类型。
- 两条历史楼中楼异常抽样的当前 API 响应中，TID／PID／FID 身份匹配；返回总数为 0 且 `has_more=false`。这无法还原旧分页异常的根因，原有 incomplete 状态继续保留；另外 8 条本轮没有重新请求。
- IDE 图形界面的 Stop 和强制结束没有现场验证。R1 的终端 SIGINT 恢复演练不能代表这两种停止方式。

## 数据保护与恢复

隔离数据库备份恢复验证通过。只读最终对照通过：原始三个数据库保持不变；指定 V5 的 13 个 CSV 与 manifest 的哈希、字节数和行数均与基线一致。该结论不涵盖含合成演练记录的隔离验收副本。公开摘要不公布哈希或采集标识。本轮没有启动新的正式采集或导出新的正式研究语料；SDK 深页验收只检查列表持久化，没有运行详情或网页采集。

恢复自己的既有回溯 run 时，使用相同论坛范围和运行模式，并填入本机日志中的 run ID：

```sh
uv run python main.py --mode backfill --resume --run-id YOUR_RUN_ID
```

这里的命令只适用于此前以 `backfill` 模式创建的 run。恢复、隔离数据库、新策略自动化回归和有限 SDK 列表写入验收均已通过；2021 年以来的完整可达性未证明，因此不建议现在启动以 2021—2026 全量完整为前提的正式采集。
