# 评论第 1 页身份失败复核

## 诊断

失败的 `get_comments` 响应在 aiotieba 原始对象和标准 DTO 中都没有可用的第 1 页身份，因此采集器按完整性错误保留了失败。与一个已知有楼中楼的正例比较后，适配层没有丢失页码字段的迹象。对其中一个失败父楼的单次 `get_posts` 复核精确匹配了 PID/TID/FID/作者，并从 protobuf wire 读到显式 `sub_post_number=0`。这只证明该父楼当前无楼中楼，不能推广到其他失败目标。

## 修复

新增默认关闭的 `--revalidate-failed-comment-page-zero` 恢复选项。它只在旧评论第 1 页失败、无后续 checkpoint、无规范评论记录且父子 scope 仍属同代时触发。采集器根据已存正楼层和父主题页大小选择一个候选帖子页，只请求一次，并要求帖子页中的完整身份及显式 wire 零值全部匹配。候选页只是定位方式，不作为完成证据。

通过复核后，事务会锁住父、子 scope 并重验代际及现有数据，再将 scope 记录为 `fresh_parent_api_explicit_zero`。checkpoint 保留旧失败和本次评论页身份失败快照、父页证据及观察时间；评论 API 的页数、数量和条目数不伪造。恢复状态将该 scope 作为完成项处理。未通过任一检查时保持失败/未完成。

## 验证范围

- 离线 handler 回归覆盖默认关闭、成功的单候选页、缺少目标/零值 presence、非零值及身份不匹配，以及 5 条正常评论不触发复核。
- 独立临时 PostgreSQL 回归验证同代原子完成、旧失败快照保留、JSON 序列化、恢复页为 `None`，并拒绝变代、已完成 scope、后续页、规范评论记录和无显式 wire 零值。
- 测试未访问生产数据库，也未写入生产数据。当前运行中的旧进程不会加载该代码；它只在使用该选项启动的后续恢复进程生效。

## WEB readiness 诊断边界

用户报告手动 headed audit 关闭前已显示正常帖子正文。随后唯一一次受控 headless 导航在官方贴吧地址返回 HTTP 403，现有 gate 检查判为安全验证；按停止条件未读取 DOM，也未重试。两次观察的浏览器模式和验证状态不同，因此当前不能判定 readiness selector 是否过严，也不把 WEB 视为已恢复。

新增诊断只在 page readiness 超时路径读取一次页面结构，最多等待约 0.75 秒：固定 URL 类别、主文档状态、`document.readyState`、当前阶段、相关选择器数量/可见数量、已捕获请求计数和已有页面/展开上限。总资源请求预算没有配置，明确记录为 unknown。诊断不读取正文、完整 URL、查询参数或 Cookie，不改变 timeout、身份判断或恢复规则；诊断期间确认到验证页或 429 时仍优先标记为 blocked。

原始 web-audit JSON 位于本机 `test-data/v2-web-audit/`，不进入 Git。
