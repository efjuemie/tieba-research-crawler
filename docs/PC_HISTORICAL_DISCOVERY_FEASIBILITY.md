# 历史主题发现与回溯可行性验证

**状态：2026-11-16 验证报告。** 可选 API REPLY 历史发现入口已通过独立代码审查、整仓离线测试和合成 PostgreSQL 集成检查。连续 API 列表实测覆盖自然页 1–1004，并在高重复保护处以 incomplete 停止。PC“发布”列表仍只验证到第 2 页。报告结果是可审计的列表样本和停止边界，不证明目标贴吧全部历史主题、正文或回复已被发现或采集。

## 已核实的基线

- `.venv` 使用 Python 3.12.16、aiotieba 4.8.2、tiebameow 0.5.0、pytest 9.2.0、Ruff 0.17.5、SQLAlchemy 2.1.8 和 asyncpg 0.32.0。
- 整仓测试：`695 passed, 10 skipped, 18 warnings`。Ruff、Python compile 和 CLI 帮助检查通过；独立代码审查通过。10 个 skip 是需显式启用的集成项。另有 8 项合成 PostgreSQL 隔离验收通过；该验收不发外部 HTTP，也不使用真实帖子数据。
- 只读数据保护复核：三个受保护源库的 45 张公开表，其行数、主键集合 SHA-256 和全列行集 SHA-256 均与既有 Gate 0 基线匹配。旧 V5 的 13 个 CSV 及 manifest 的哈希、字节数和行数匹配；旧深扫报告哈希未变。检查使用只读事务和精确数据库身份守卫，没有写入源库或旧导出文件。
- 隔离库的 `research_thread` 有 8,599 行，其中 15 行可依据合成论坛/检查点元数据识别为合成行，且 `reply_count` 均为空。其余 8,584 行没有合成标记；仅凭未标记不能证明每行均为真实研究语料。
- Gate 1 的实测为 **INCONCLUSIVE**；共 18 个受控页面动作，没有修改采集源码或写入数据库。PC 列表页面请求已停止。Gate 2 只读核验使用 3 次 API 请求，均返回 HTTP 200，没有数据库写入或客户端改动。旧深扫 run 仍为 incomplete，未排空详情任务。

已实现的回溯入口保留默认 `CREATE/rn=30`，可显式选择实验性 API `REPLY/rn=100`；周期首页继续使用 `REPLY/rn=30`。历史 REPLY 发现流与默认 CREATE 使用独立 run、scope 和 checkpoint。既有详情、字段来源与水位、租约和网页补采流程未修改。

此前隔离实测记录的 SDK `CREATE` 页 334 返回 `has_more=false`、`total_page=334`；单独请求第 335 页返回空页且仍报告 `total_page=334`。该证据说明那次 SDK 列表调用没有报告后续页，**不证明所有列表入口的统一上限**。PC 页面使用的 `/c/f/frs/page_pc` 与 SDK 的 `/c/f/frs/page` 不同。此次“最新”首页 `sort_type=0` 报告 `total_page=11030`、`total_count=330875`；“发布”首页 `sort_type=1` 报告 `total_page=334`、`total_count=9998`、`has_more=true`。另有未选排序的 `sort_type=-1` 首页记录报告 `total_page=11030`、`total_count=330879`，记录中部分创建时间可追溯至 2018 年；该请求没有完成置顶和既有 SDK 重叠核对，不能将其作为“最新”或“发布”流证据。这些均为首页服务端元数据，不是深页或终止页证据；不能据此声称 PC 与 SDK 同限或历史覆盖范围。

## Gate 1：PC 发布列表初步观察

共 18 个受控页面动作：前两轮 8 次，定向滚动复测 10 次，其中复测含 3 次导航/排序、7 次鼠标滚轮。项目隔离 Profile 登录正常；官方吧首页及“最新”“发布”页面均返回 HTTP 200。从“最新”切换到“发布”时观察到 `POST /c/f/frs/page_pc`，请求中的 `sort_type` 从 0 变为 1，论坛归属一致，页码为 1、请求数量为 30。响应字段 `tab_name` 仍显示“最新”，因此不能单独用该字段判断最终排序。

复测定位到滚动容器 `.frs-page-wrap.styled-scrollbar.deep`，其 `overflow-y=scroll`、`clientHeight=940`。7 次滚轮操作令 `scrollTop` 从 0 到 6,300；页面动态 `scrollHeight` 为 10,075，记录结束时距底约 2,835 像素。第 7 次滚轮触发了真实 `POST /c/f/frs/page_pc` 第 2 页：`sort_type=1`、请求与响应论坛归属一致、`current_page=2`、`total_page=334`、`has_more=true`、`offset=30`，HTTP 200。该页有 30 个唯一 TID，与第 1 页交集为 0；只有 10 条创建时间可可靠解析，时间范围为 2026-11-13 至 2026-11-14，不能把这 10 条当作整页最早/最晚范围。滚轮 1 和 4 触发的 `threadlist_pc` 响应属于同页水合或索引加载，不计作新的 `page_pc` 页。

至此确认发布列表可从第 1 页推进到第 2 页；该流尚未观察到第 3 页或窗口外主题。`scrollTop` 尚未到达列表底部；本次也未确认可用的正常跳页控件。先前的 `window.scrollY=0` 是视口滚动值，不代表列表容器未滚动。Gate 1 仍为 **INCONCLUSIVE**，不能判定 PC 与 SDK 同限。

PC 列表请求已停止。另在未选排序 `sort_type=-1` 首页离线发现一个约 2022 年的旧帖候选：同一卡片内可见的主题身份字段相符，贴吧归属也一致；该候选不在当前核对的 SDK `CREATE` 第 1–334 页集合或精品集合中。但没有显式的非置顶证据，因此它只是其他排序入口的定向旧帖候选，不能作为普通“发布”列表跨过 SDK 窗口的证明，也不能作为 Gate 1 通过证据。

预算示例：若暂把首页报告的 334 页作为计划规模，并假设每页至少需要一次受控动作、动作间隔为 5 秒，从第 1 页走到第 334 页约需 333 次后续动作，即约 27 分 45 秒。这只是动作频率预算示例，不是实测耗时或数学下界；一次浏览器动作可能触发多个自动请求，真实滚动、页面加载和等待也会增加用时。本次没有深扫。

## Gate 2：定向旧帖详情只读核验

针对上述未选排序首页候选，现有 `ResearchClient` 共发出 3 次 HTTP 请求，均返回 200；每次都通过 `global_rps=0.2` 的请求预算，没有写数据库。`get_posts` 请求第 1 页、每页 30 条且不内嵌评论，返回 15 个原始楼层对象：其中 1 个首楼与主题身份、贴吧归属、作者及日期核对相符，另有 14 个唯一一级回复 PID。独立首楼内容核验确认 raw 与 DTO 正文均非空且一致；没有复制或保存正文内容。

在 14 个一级回复中，有楼层报告含子回复。对一个确认的父楼调用一页 `get_comments`，得到 6 个唯一 CID；响应范围及每条子回复的 TID、FID、父 PID 与请求一致，且均包含作者 ID。该核验只证明这个约 2022 年样本可通过现有 API 读取首楼、一级回复和一页楼中楼；不证明未选排序入口可连续枚举、普通“发布”列表已跨窗或全部历史可达。Gate 2 对此样本为 **DETAIL-API-PASS**，不改变 Gate 1、Gate 3 或 Gate 4 状态。

## 既有研究与当前入口

一篇 2019 年针对同一贴吧的研究报告称，其 Scrapy 爬虫处理了 2007 年 8 月至 2018 年 7 月的主题，并统计 113,243 个主帖。论文没有说明当前接口的请求路径、分页游标、终止条件或如何复现历史页；其中关键词方法用于后续感染者筛查，也不能据此推断采集阶段按关键词筛选了主题。[论文原文（DOI: 10.11959/j.issn.2096-271.2019008）](https://doi.org/10.11959/j.issn.2096-271.2019008)

另一项研究分析的是贴吧里的白化病社区，并非本项目的目标贴吧。作者报告曾爬取 2007—2019 年记录，但说明 2012 年前数据严重缺失且零散，因此后续分析使用 2012—2019 年数据。[JMIR 论文原文](https://medinform.jmir.org/2020/5/e17813/)

这些论文说明研究者曾报告获取多年 Tieba 语料；它们不能证明当前 PC 或 SDK 列表仍可复现这些年份、可连续枚举，或覆盖完整。当前官方入口与分页结论仍以 Gate 1–3 的实测为准。

## 后续 API REPLY 历史发现验证与最小接入

页 1000 和 1001 分别产生 97 和 95 个新 TID。页 1002 返回 100 条，其中 99 条已见、1 条为新；页 1003、1004 返回与页 1002 完全相同的 100 个 TID 集合。按非置顶 TID 计算，页 1002–1004 连续达到三页高重复条件：第 1002 页有 96/97 个非置顶 TID 已见，第 1003、1004 页各有 97/97 个已见；三页各含 3 个置顶主题。第 1004 页观察记录已保存后，探针以 `paused_high_repetition_incomplete` 停止，`completed=false`；没有请求第 1005 页。这是重复保护边界，不是服务端自然终点。

第 1004 页响应仍带 `has_more=true`，服务端报告 `total_page=3309`。该 metadata 不参与页号上限或完成判定，也不证明 3309 页或约 33 万条记录可达。停止状态仅说明探针按真实响应连续前进至观察到的高重复区域，并执行保护；不能声称全站覆盖。

当前工作区提供的产品入口是 `--mode backfill --backfill-sort reply`；原 `--mode backfill` 仍默认为 CREATE/rn=30，周期 REPLY 首页仍为 rn=30。历史 REPLY 使用 `reply_backfill` 独立持久 run、页 checkpoint key 和 scope fingerprint，固定 API 来源 `aiotieba.get_threads`、sort_type=6、rn=100、普通列表，并严格核验 raw/DTO 页号、FID 和 TID 集。REPLY 页数/条数 metadata 只记录，不用于分页上限。该功能复用既有发现后详情处理、checkpoint、回复/评论详情、字段补采及 CSV/export 路径；页面索引发现不等于详情已采集。

此入口的保护规则是在连续 3 个自然新页各自至少 90% 的非置顶唯一 TID 已见时，先保存第三页和新增 TID，再将 run 标记为 incomplete 并暂停；恢复重读允许同页 ID 漂移并合并观察，不更改重复 streak。单个 `has_more=false` 高重复页，以及只有置顶主题的非空终止页，也不能作为可信终止。运行到服务端终点至多记录“观察到服务端终止”；只有另行审核连续页、身份、重复及详情排空证据后，才可描述该 run 的范围，仍不能声称是贴吧全站全部历史。验证探针产生的 `INDEX_ONLY` 输出仅包括列表索引字段，不能作为正文或回复完成的证据。

最小产品接入已通过独立代码审查、整仓离线回归及 8 项合成 PostgreSQL 隔离验收；合成数据库只写入伪造的小型 fixture，外部 HTTP 数为 0。正式产品入口尚未用于这段真实 API 连续采集，API 采样由独立探针执行。代码回归、合成持久化和真实 API 列表观察是不同证据，不能相互替代。
